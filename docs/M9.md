# M9 — connected player movement and camera response

## Result — held left-stick turn and camera response verified, 2026-11-16

**Resume here.** M9 reconstructs one continuous player-controlled operation of
the original Japanese game (SCPS-15046, ELF SHA-256 `a74248c5…3c61`): **holding
the left stick left turns the player, and the camera follows in the same frame.**
The operation is compared exactly with one continuous original run (PCSX2
v2.8.2, PINE slot 28059, default settings) over the neutral frame, five held
frames, the release frame and the frame where the rate reaches zero.

**input 3eaf0c = −1.0 → 159570 active update → 159ad0 ordinary update →
15fe00 gate (a1 = 1) → 15fe70 movement → 1608b0 walk → 160510 turn (rate +440,
heading +44) → return → 12c790 camera update → 12d130 follow → 12bd00 head
matrix → look-at 12c3d0 (camera yaw 3f9934) → view matrix at scratchpad 70000000**

"0 / 0 B" means 0 differing bytes in EE RAM (33,423,360 compared bytes) and
0 in the scratchpad (16,384 bytes). \*The capture names release1–3 were assigned
when the key-up was sent. Input latency kept the stick held for three more frames
(3eaf0c = −1.0 in those captures), so they are held-stick frames. They were not

stick was not yet visible there.

The turn ramps the rate by −π/4000 per frame (level 3, table 39a3f0) and decays it
by π/1200 per frame after release. The heading becomes `wrap(+44 − rate)`. The
camera yaw 3f9934 is recomputed by atan2 in 12c3d0 rather than copied, so it can
differ from the player heading by 1 ULP. The original does the same, and the C
matches it exactly. View-matrix row 0 rotates on every frame.

### What changed

- **M8 defect corrected.** The original 00159ad0 calls 0015fe00 with **a1 = 1**:
  the delay slot at 00159b08 (`li a1,1`) always executes. M8's C passed 0. That
  was indistinguishable with neutral input, but it suppresses turning and walking
  (turn frames differed at 3f9314, 3f9710 and 3f97d4). M8's ordinary-update
  differential hid it by declaring 0015fe00 with arity 1. The arity is now 2, and
  that differential rejects the M8 source (`external call trace differs …
  (0x15fe00, 0x500000, 1)`).
- **Reconstructed in C** (packet [player_turn_camera](../analysis/player_turn_camera/README.md),
  11 routines, 1,147 words / 4,588 bytes): 15fe00, 15fe70, 1608b0, 160510,
  160420, 15fcd0, 160c20, 1204e0, 12d130 complete; **12c790 and 12bd00 for their
  observed branches only**. The other branch calls the host-only fail-closed
  `HG_DOMAIN_FAULT`.
- **Integer-exact FP in C** (`hg_ee_fp`): chop, DAZ/FTZ, ±FLT_MAX saturation,
  EE add guard bit, exact-then-chop VU add; non-finite operands fault.
- **Model (`tools/ee_subset.py`)**: VRSQRT, VDIV (chop; a zero divisor fails
  closed), VOPMULA, VOPMSUB, VNOP, vmulq, pextlw/pextuw/pcpyud, xor, nor. Each
  was demanded by an observed original instruction. A wrong VOPMSUB lane order was
  found during development (it zeroed the look-at cross product at 102b98) and
  fixed before any comparison was recorded.
- **Bus FP seam convention** (both runtime drivers): raw-bit FP operands first
  (f12…), then integer arguments (a0…), result from f0 where declared.
- `tests/resource_sanitizer.c`: the M8 player leaf set gained the M9 movement
  leaves. CI's sanitizer step would otherwise abort, because 15fe00 now resolves
  in C. An M9 turn/camera composition is added.

Handoffs: on every frame, the C-produced turn fields (heading, rate, levels,
pitch, speeds, position) equal the native camera-entry capture and the next
frame's update entry. The C-produced camera yaw/pitch equal the next frame's
entry. Between update return and camera entry, the only actor byte changed is
+42b, by code outside this reconstruction (as M8 recorded).

### Controls

- **Input counterfactuals** on real entry states, each required to diverge with
  the expected behaviour: turn1 stick 0 (rate stays 0; 9 bytes differ); turn1

- **Compiled retail defects** that must be rejected: gate a1 = 0, wrong stick
  source, missing sign negation, skipped heading write, heading adds the rate,
  wrong scale table, wrong limit column, camera heading from the rate, camera
  without view yaw, wrong eye height, VU add with the EE guard bit (11).
- **Model defects** that must be rejected: VOPMSUB sign (ACC + product instead
  of ACC − product), EE add without guard bit in the model, VDIV rounded to
  nearest (3).

A control counts as **rejected only when its comparison completes and measures
a divergence**: a failed stage, handoff or operation check, or a call-trace,
memory, return or register mismatch. Any exception (bus or driver error, domain
fault, model error, verifier defect) is reported as `error` and fails the run.
- **Instruction-differential defects** that must be rejected: missing sign
  negation, decay without zero clamp, wrong dead zone, swapped brake branch,
  wrong target depth, EE add without guard bit, VU add with guard bit (7).

### Discrepancies found and resolved

- **VDIV by zero.** An x/0 → ±FLT_MAX rule (microVU behaviour) was added while
  the VOPMSUB lane order was still wrong, which zeroed the look-at cross product.
  A measurement on the correct model showed that VDIV runs twice per camera
  update but never with a zero divisor in any captured frame, so the rule was
  unobserved. VDIV by zero now fails closed, like a zero VRSQRT radicand.
- **The C EE guard bit is insensitive on retail data.** Removing the guard mask
  from the C `add.s`/`sub.s` does not change the observed operation; that much is
  measured. The likely reason, which was not separately instrumented: the
  observed adds combine same-sign operands, where a chopped result ignores bits
  below the guard, or operands with equal exponents. That control therefore runs in
  the instruction differential and the synthetic FP tests, which do reject it.
  The model's guard bit is retail-sensitive and rejected on 7 camera stages.
- **Ineffective control replaced.** A VU-add control on the second accumulation
  (`m[4+lane]·v.y`) was equivalent, because 12bd00's vector is always
  (0,0,20,1). The control now mutates the final `+ m[12+lane]·v.w` term.
- **An exception was counted as a rejection.** The first M9 runtime verifier
  treated any exception during a control as a rejection. Once VDIV by zero
  failed closed, the VOPMSUB lane-order model control zeroed the cross product
  and was "rejected" only by that `ValueError`, not by a measured divergence.
  The evidence committed in `e0c1f5c` recorded it that way, so that record
  over-states one rejection. Commit `6062f0e` fixes the rule in both M9 verifiers
  and applies it to the M8 runtime controls. M8's synthetic connected controls now
  also refuse a test failure caused by recorded driver errors. The lane-order
  control was replaced by the VOPMSUB sign defect, which fails 7 camera stages
  with no exception. Rerun, the old lane-order mutation is reported as `error`. No
  other M8 or M9 control had relied on an exception.
- **Output-stem collision in the private regression runner.** See check 21 below.

### Limits

- Hybrid reconstruction: C turn/camera control plus original-instruction-modeled
  leaves (strafe 160c60, 160ff0, 15fd30, 1606e0, 15ebc0, 15fc10, 15aea0, distance
  120830, atan2 120580, sin/cos 143560/143620, rotations 143c60/143d30/143b90,
  12c640, 12cce0, look-at 12c3d0, 15e1d0, 13a240, 267450). This is not all-C,
  whole-game equivalence, static recompilation or byte matching.
- Only one operation is observed: a left turn at speed class 1, level 3, without
  walking, strafing, look mode, camera shake or pitch. The other 15fe70/1608b0
  branches are differentially tested against the original instructions only.
- 12c790 (3eaed4 ≠ 0) and 12bd00 (+47a ≠ 0) are not reconstructed; they fail closed.
- The FP model is functional: no FP flags, exceptional values or timing. Results
  depend on PCSX2 v2.8.2 default rounding/clamping settings.
- Release1–3 are held-stick frames despite their names (see above).
- This M9 run reuses the M8 seeded camera matrix only in the unchanged M8
  regression; M9's own comparisons use captured scratchpad entry state and compute
  the camera.
